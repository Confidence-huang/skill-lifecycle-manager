# V5.2 Skill Lifecycle Guardian Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a cross-platform daily Skill guardian that scans every canonical Registry record, writes evidence reports, and requires an exact human approval before a source update can mutate production.

**Architecture:** Keep `skills-registry.json` as the only observed-state authority. Add a separate Guardian policy for desired monitoring rules, a deep `guardian` module for policy/scan/approval orchestration, and platform-owned schedule installation. Scheduled work may write only Guardian reports; update application remains a separate explicit transaction.

**Tech Stack:** Python 3.12 standard library, argparse, JSON Schema Draft 2020-12, Git argument arrays, Linux systemd user timers, Windows Task Scheduler, unittest, uv.

## Global Constraints

- Release as V5.2.0; do not create a second Registry authority.
- `guardian scan` must inspect all Registry records and must never install, fetch, merge, activate, or upgrade a Skill.
- `guardian scan --apply` may write only immutable/latest Guardian JSON and Markdown reports.
- Compatibility is `UNKNOWN` unless a declared probe supplies direct evidence.
- Production source updates require an unexpired approval bound to the exact report, current commit, candidate commit, Registry fingerprint, and policy identity.
- No policy tier authorizes unattended production updates in V5.2.
- Do not edit arbitrary project `PROJECT_LOG.md` files; reports remain standalone evidence for deliberate human incorporation.
- Keep Linux and Windows scheduling behind the existing platform seam; schedule installation previews by default and refuses to overwrite an existing schedule.
- Preserve the formally installed V5.0 manager and host-local lifecycle state unchanged while developing this public V5.2 candidate.
